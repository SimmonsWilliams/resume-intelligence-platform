# Stage 2 — Integration Architecture and Implementation Plan

**Scope:** Planning only. This document recommends implementation changes. It does not modify application code, create modules, install dependencies, run processing, or deploy the application.

## 1. Proposed Architecture

The application will retain the existing batch scripts and report-driven dashboard, with three explicit runtime modes:

- **Existing Local Reports Mode:** uses only locally available report data already generated by the batch workflow.
- **Demo Mode:** uses only committed, clearly fictional synthetic candidates and synthetic job descriptions. It must never read private local candidate folders.
- **Resume Analysis Mode:** is a session-only upload workflow intended for Stage 4 and later. Stage 3 may display all three runtime modes—Existing Local Reports, Demo, and Resume Analysis—but Resume Analysis Mode must remain a placeholder until Stage 4. It must not expose an upload control or accept, parse, analyze, match, score, download, or otherwise process any upload in Stage 3.

Original `resume_analyzer_v2.py` processing is not implemented by the Stage 3 UI. The Stage 3 Resume Analysis placeholder must clearly state that upload processing is unavailable until Stage 4 approval and implementation.

The recommended integration is a thin orchestration module plus small edits to `app.py` and existing parser utilities. Existing parsers, analyzers, matchers, validators, project logic, and scoring logic remain the business-logic owners.

```text
                         Streamlit app.py
                 ┌────────────┼────────────┐
                 │                         │
           Demo Mode               Resume Analysis Mode
                 │                         │

                 │                         │

                                         BytesIO

### Integration principles

1. Do not rewrite all of `app.py`; add mode/state orchestration and delegates.
2. Do not import or modify `resume_job_matcher_fixed.py` for the upload path.
3. Use `resume_job_matcher.py` because `scoring_engine.py` already imports it.
4. Use `resume_analyzer_v2.py` because it provides evidence and ontology metadata.
5. Preserve existing batch CLI behavior and existing dashboard pages.
6. Avoid persistent storage of uploaded resume text. The `processing_id` is an ephemeral in-session identifier, not a disk name.
7. Do not automatically reject or rank a lone resume as a hiring decision.

### Strict runtime mode isolation

The application must expose exactly three distinct runtime modes. Switching modes must replace the active data source and must not combine records across sources.

#### Existing Local Reports Mode

- Used only in a local repository environment where the user explicitly selects the existing report workflow.
- May read `analyzed_data/`, `reports/`, and report JSON/CSV files, because those are the existing local batch outputs.
- Must remain separate from synthetic and upload data.
- It is not the default deployment mode and must not be required for Community Cloud startup.
- Missing or malformed local reports produce a missing-data state; they must not trigger Demo Mode or a synthetic fallback automatically.
- This mode must never be activated merely because a private report is absent. The absence of private data must not cause synthetic records to be silently mixed into local results.

#### Demo Mode

- Uses only committed, public-safe synthetic candidate and synthetic job fixtures.
- Must not read, list, probe, import, or otherwise access `analyzed_data/`, `analyzed_data_v2/`, `extracted_data/`, `Resume docs/`, or `reports/`.
- The implementation should enforce this by using a separate fixture loader and no private-report loader calls in the Demo Mode branch.
- Synthetic and private data are never merged, even when private reports are partially missing.
- Every displayed page and exported record must clearly show `DEMO DATA — FICTIONAL CANDIDATES` and the decision-support disclaimer.

#### Resume Analysis Mode

- Uses only the one resume currently selected in the upload control and the one job description currently selected for that resume.
- Does not load local candidate profiles, private reports, synthetic candidate records, or synthetic candidate rankings.
- May read public, committed job-description data only, or dedicated fictional demo job fixtures.
- It is session/state ephemeral and must clear previous upload results when the uploaded file or current analysis is cleared or replaced.
- It must not rank or compare the upload against any other candidate. The existing `evaluate_candidate_job()` call may produce component and overall values for the selected resume/job pair only; it must not imply selection or rejection.

## 2. Audit Corrections

### 2.1 In-memory DOCX extraction

`python-docx.Document()` accepts a filesystem path or a binary file-like object. A Streamlit `UploadedFile` can be converted to `io.BytesIO(uploaded_file.getvalue())` and passed to `Document(stream)`. The proposed implementation should test this explicitly before finalizing:

- seek the `BytesIO` to offset zero;
- call `Document(buffer)`;
- read paragraphs and tables;
- never write the original upload to disk;
- catch `zipfile.BadZipFile`, `PackageNotFoundError`, and parser/OSError exceptions.

The existing `extract_text(file_path)` signature should remain intact for batch compatibility. A shared private function can extract from an already-created `Document`, and a new `extract_text_from_stream(stream)` function can serve uploads.

### 2.2 Actual V2 analyzer output

`resume_analyzer_v2.analyze_candidate(candidate, patterns)` returns:

```python
{
    "candidate_id": str,
    "source_file": str,
    "skills": list[str],
    "skill_evidence": list[dict],
    "potential_skill_candidates": list[dict],
    "education": list[str],
    "experience": list[str],
    "experience_evidence": list[str],
    "projects": list[str],
    "certifications": list[str],
    "professional_summary": list[str],
    "awards": list[str],
    "section_counts": dict[str, int],
    "extraction_status": "ANALYZED",
    "verification_required": True,
    "analyzer_version": "2.0",
}
```

It does not return `experience_level`, `manual_review`, or a structured education degree object.

### 2.3 Exact scoring contracts

#### `evaluate_candidate_job(candidate, job, project_result, quality_result)`

The function signature and direct assumptions are exact:

- `candidate: dict`: required for `candidate.get()` calls and for `candidate["candidate_id"]`. `candidate_id` must be a non-empty `str`; the function calls `.strip()`.
- `job: dict`: required for `job.get()` calls and for `job["job_id"]`. `job_id` must be a non-empty `str`; the function calls `.strip()`. `job_title` is optional at the `.get()` level and may be `None`, but the dedicated demo job contract should require a non-empty string.
- `project_result: dict | None`: normally one return value from `match_candidate_projects()`, or `None` when unavailable.
- `quality_result: dict | None`: normally one return value from `validate_candidate()`, or `None` when unavailable.

It also directly reads these candidate keys:

- `manual_review`: optional list; non-list values are ignored.
- `verification_required`: optional boolean; only exactly `True` adds the verification review reason.
- `skills`: passed by the skill component; must be a list/tuple containing only strings. Missing, malformed, or empty values become component review states or unspecified behavior as implemented.
- `education`: string, list, or tuple for education scoring.
- `experience` and `experience_evidence`: consumed by `match_experience()`; the experience matcher expects list/tuple text entries and otherwise handles absent values conservatively.

#### Exact project-result contract

A direct call to `project_matcher.match_candidate_projects()` returns this shape:

- `candidate_id: str`
- `source_file: str`
- `job_id: str`
- `job_title: str`
- `status: str`: one of `NO_PROJECT_DATA`, `BELOW_MINIMUM_PROJECT_COUNT`, `PARTIAL_MATCH`, or `MATCHED`
- `project_count: int`
- `minimum_projects`: numeric value or `None`
- `project_count_evaluated: bool`
- `project_count_met: bool | None`
- `projects: list[dict]`; each grouped project has `title: str`, `description_lines: list[str]`, and `full_text: str`
- `matched_required_skills: list[dict]`, each match has `name: str` and `evidence: list[dict]`
- `missing_required_skills: list[str]`
- `matched_preferred_skills: list[dict]`
- `missing_preferred_skills: list[str]`
- `matched_software_tools: list[dict]`
- `missing_software_tools: list[str]`
- `grouping_note: str`

The exact project match evidence shape used by scoring is:

```python
{
    "name": str,
    "evidence": [
        {
            "project_title": str,
            "matched_text": str,
        }
    ],
}
```

Malformed project evidence is not converted into a high-confidence match: `_matched_names()` returns `None` if matched lists are not lists or entries are not dictionaries with string `name` values.

#### Exact quality-result contract

The upload workflow should pass the actual dictionary returned by `data_quality_validator.validate_candidate()`:

- `candidate_id: str`
- `source_file: str`
- `validation_status: str`: `VALID`, `REVIEW_REQUIRED`, or `INVALID`
- `issue_count: int`
- `warning_count: int`
- `issues: list[str]`
- `warnings: list[str]`
- `missing_optional_sections: list[str]`

Scoring is tolerant of `None`, but if a dictionary is present it reads `validation_status`, `issues`, and `warnings`. It appends a data-quality review reason unless `validation_status == "VALID"`, and appends every issue and warning.

#### `manual_review`

`evaluate_candidate_job()` builds `manual_review_reasons` as a deduplicated list. It adds:

- `"Candidate profile is marked verification_required."` when candidate verification is true;
- each string item in candidate `manual_review`, if the key is a list;
- quality status, issue, and warning messages;
- component notes whose component `requires_review` is true;
- missing project-report or `NO_PROJECT_DATA` messages;
- project grouping notes when projects and a grouping note are present.

`manual_review_required` is `bool(reasons)`. This is a review indicator, not a hiring decision or rejection flag.

#### `component_coverage` and score fields

The five component keys returned as component point fields are:

- `required_skills_score`
- `preferred_skills_score`
- `education_score`
- `experience_score`
- `project_score`

Each is `float | None` and is constrained by its existing component weight:

- required skills: 25 points;
- preferred skills: 10 points;
- education: 15 points;
- experience: 25 points;
- projects: 25 points.

`component_coverage` is a dictionary with those five names mapped to percentages rounded to two decimal places:

```python
{
    "required_skills_score": float,
    "preferred_skills_score": float,
    "education_score": float,
    "experience_score": float,
    "project_score": float,
}
```

Coverage values are 0.0–100.0. The return also includes `component_notes: dict[str, str]` containing only components with notes.

#### Existing formula and ranges

The existing engine preserves this normalization formula:

```text
weighted_capacity = sum(component.weight * component.coverage_fraction)
earned_points = sum(component.points or 0.0)
overall_score = earned_points / weighted_capacity * 100.0
               if weighted_capacity > 0 else None
score_coverage = weighted_capacity
```

- Each component point is 0 to its configured weight.
- `overall_score` is 0.0–100.0 when `weighted_capacity > 0`; it is `None` when no weighted capacity is available.
- `score_coverage` is 0.0–100.0 weighted points of available evidence.
- `evaluation_status` is exactly `EVALUATED`, `PARTIAL_DATA`, or `MANUAL_REVIEW` based on actual reasons and coverage.
- Missing or unavailable components are excluded from denominator/capacity according to the existing component logic. Do not replace this behavior with a fabricated zero or 100.

The V2 profile is schema-compatible after list/default normalization, but it does not change or supersede these source contracts.

### 2.4 Minimum profile adapter

Create a function similar to:

```python
def adapt_v2_profile(profile, processing_id, source_label="uploaded_resume"):
    adapted = dict(profile)
    adapted["candidate_id"] = processing_id
    adapted["source_file"] = source_label

    list_fields = (
        "skills", "education", "experience", "experience_evidence",
        "projects", "certifications", "professional_summary", "awards",
    )
    adapted.setdefault("manual_review", [])
    for field in list_fields:
        value = adapted.get(field)
        if isinstance(value, tuple):
            if field in ("skills", "education", "experience", "experience_evidence"):
                if all(isinstance(item, str) for item in value):
                    adapted[field] = list(value)
                else:
                    adapted[field] = value
                    adapted["manual_review"].append(
                        f"Adapter validation failed for tuple value in {field}; manual review required."
                    )
            elif all(isinstance(item, dict) for item in value):
                adapted[field] = list(value)
            else:
                adapted[field] = value
                adapted["manual_review"].append(
                    f"Adapter validation failed for tuple value in {field}; manual review required."
                )
        elif not isinstance(value, list):
            adapted[field] = []

    adapted.setdefault("verification_required", True)
    adapted.setdefault("extraction_status", "ANALYZED")
    return adapted
```

Additional adapter behavior:

- replace the original filename with a generic, session-only source label;
- generate `UPL-<short UUID>` for `candidate_id`;
- preserve V2 evidence structures;
- normalize absent lists without changing discovered values;
- preserve `skill_evidence`, `potential_skill_candidates`, and `section_counts` for display/download;
- do not copy personal text into logs or filenames;
- tuple values are valid collection inputs and must not be silently discarded or converted to empty values;
- for `skills`, `education`, `experience`, and `experience_evidence`, validate every tuple element as a string, then normalize the tuple to a list with `list(value)`; if any element is not a string, preserve or reject the tuple explicitly and add a manual-review or validation finding, rather than replacing it with an empty list;
- for tuple values in list-only evidence/container fields, normalize them to lists only after validating every element against the field's contract (for example, evidence dictionaries with the required keys); otherwise preserve or reject the tuple explicitly and add a manual-review or validation finding;
- absent or non-tuple, non-list values may be normalized to an empty list only when the field is absent or empty, and this normalization must not be used to discard a non-empty tuple or other discovered data;
- never infer or fabricate tuple element values;
```

### 2.5 Data quality validator correction

The audit should not describe `validate_candidate()` as duplicated. The source contains one definition of `validate_candidate()` at line 82. `validate_all_candidates()` calls that function at line 366 and is the batch wrapper. The actual risks are:

- batch paths default to ignored `analyzed_data/` and `reports/`;
- the validator requires `candidate_id` and `source_file` in `REQUIRED_FIELDS`;
- important fields are `skills`, `education`, and `experience`;
- optional fields include `projects`, `certifications`, `professional_summary`, and `awards`;
- upload profiles need the adapter's normalized list fields and generic source label;
- `validate_candidate()` should remain the reusable function; `validate_all_candidates()` should remain batch-only and should not be invoked by the Streamlit upload workflow.

### 2.6 Project and job contract

`project_matcher.match_candidate_projects(candidate, job)` reads:

- `candidate["projects"]`
- `job["required_skills"]` or `[]`
- `job["preferred_skills"]` or `[]`
- `job["software_tools"]` or `[]`
- `job["experience"]["minimum_projects"]` if present
- `candidate_id`, `source_file`, `job_id`, and `job_title` for report fields

The function ignores non-list or malformed project values through `candidate.get("projects", [])`, but upload orchestration should still validate and normalize job fields before calling it.

Scoring's project component also reads:

- `project_count`
- `projects`
- matched required/preferred/software evidence
- `job["required_skills"]`, `job["software_tools"]`, and `job["experience"]["minimum_projects"]`.

The matcher is deliberately literal; it is not a semantic or fuzzy project matcher.

## 3. Module Integration Diagram and Data Contracts

### Upload processing contract

```text
UploadedFile
  -> validate_upload() -> {valid, processing_id, error, size_bytes}
  -> extract_text_from_stream() -> candidate input text
  -> build_extracted_candidate() -> {candidate_id, source_file, full_text,
                                    character_count, extraction_status}
  -> load_ontology() -> skill map
  -> compile_skill_patterns(skill map) -> patterns
  -> analyze_candidate(candidate, patterns) -> V2 profile
  -> adapt_v2_profile(profile, processing_id) -> scoring-compatible profile
  -> validate_candidate(profile) -> quality result
  -> load selected job -> job dictionary
  -> match_skills(profile skills, job) -> required/preferred evidence
  -> match_education(profile education, job) -> education evidence
  -> match_experience(profile, job) -> experience evidence
  -> match_candidate_projects(profile, job) -> project evidence
  -> evaluate_candidate_job(profile, job, project_result, quality_result)
  -> session-only result payload -> Streamlit tables/cards + CSV/JSON downloads
```

### Scoring return contract

`evaluate_candidate_job()` returns fields including:

- `candidate_id`, `job_id`, `job_title`
- component point fields
- `overall_score`
- `score_coverage`
- `manual_review_required`
- `manual_review_reasons`
- `evaluation_status`
- `component_coverage`
- `component_notes`

The UI must retain `overall_score = None` as unavailable rather than rendering it as zero. Component points remain point values. The human-review disclaimer must appear beside every uploaded result and demo score.

## 5. Synthetic Demo Mode Plan

The Demo Mode implementation will:

1. Create a public-safe synthetic fixture set under a dedicated repository folder or JSON module.
2. Use candidate IDs such as `DEMO-001` through `DEMO-N` and generic fictional names if names are needed.
3. Never source values from `analyzed_data/`, `analyzed_data_v2/`, `extracted_data/`, `Resume docs/`, or reports.
4. Display a prominent `DEMO DATA — FICTIONAL CANDIDATES` banner on every Demo Mode page.
5. Display a statement that scores are decision-support indicators requiring human review.
6. Generate only synthetic DataFrames/report records in memory or from the committed JSON fixture.
7. Create dedicated fictional demo job descriptions rather than assuming that existing sample files are synthetic.

Existing files in `job_descriptions/` are sample or public project data but must not be assumed to be synthetic Demo Mode data. A future implementation should create a separate committed `demo_jobs.json` or `demo_data/` fixture containing job IDs, titles, required/preferred skills, software tools, education, and experience fields in the exact matcher/scorer schema. Synthetic jobs must contain no real personal, organizational, location, or candidate data.

No synthetic fixture should imply an actual hiring outcome. Demo candidate records should include realistic but obviously fictional experience and project evidence.

## 6. Missing-Local-Data Plan

Before loading private/report paths, the app must know the active mode explicitly. Missing private data handling applies only to Existing Local Reports Mode.

- absent report: empty DataFrame plus a visible unavailable message;
- malformed report: empty DataFrame plus a safe error message;
- absent profile JSON: no profile records;
- absent project/scoring JSON: no detailed evidence;
- absent entire private directories: no crash and no automatic synthetic fallback;
- Existing Local Reports Mode: preserve the missing-data state and explain that private reports are unavailable;
- Demo Mode: use only dedicated synthetic fixtures and never attempt private loader calls;
- Resume Analysis Mode: use only the current upload and selected job, and remain independent from private and demo candidate records.

The app must not warn with absolute filesystem paths or expose private filenames to the browser. It must not silently switch modes or merge synthetic candidates into a partially loaded local report set.

## 7. DOCX Upload Plan

The implementation will add DOCX-only support initially:

1. `st.file_uploader(..., type=["docx"], accept_multiple_files=False)`.
2. Validate filename suffix case-insensitively.
3. Limit upload size (proposed 5 MB initial limit; final value requires approval).
4. Reject empty files, directories disguised as DOCX, and files not recognized by `python-docx`.
5. Read bytes once with `uploaded_file.getvalue()` and wrap in `BytesIO`.
6. Pass the stream to `extract_text_from_stream()`.
7. Reject or clearly mark whitespace-only text.
8. Create an ephemeral `UPL-<short UUID>` candidate ID.
9. Store only section text, profile fields, evidence, and a generic source label in session state.
10. Do not write to `Resume docs/`, `extracted_data/`, or `analyzed_data*`.
11. On rerun, keep only the current session result and clear it on removal/new upload.
12. Provide an explicit mandatory `Clear Analysis` control that removes application references to the uploaded resume bytes, extracted text, profile, match outputs, score output, and generated download payload from Streamlit session state. This is session-state cleanup only: it does not guarantee secure deletion or erasure from server process memory, OS caches, backups, garbage-collected memory remnants, or other runtime storage.
13. On a new upload, replace rather than append to the previous analysis. No previous resume may remain active when the selected file changes.

The UI must display: `Uploaded content is held temporarily in Streamlit session state for this analysis. Session state is temporary application state, not a guaranteed secure private vault or proof of secure server-memory deletion. Do not upload sensitive documents.`

PDF support remains excluded unless a separate approved design and dependency/security review is completed.

## 8. Resume Analyzer and Adapter Plan

The upload workflow will:

1. call `load_ontology()`;
2. call `compile_skill_patterns()`;
3. build a transient candidate containing `full_text`, ephemeral ID, and generic source label;
4. call `analyze_candidate()`;
5. call the profile adapter;
6. validate the adapted profile with `validate_candidate()`;
7. display extracted skills and evidence separately from unknown ontology candidates;
8. display any missing education, experience, project, or quality fields;
9. explain that extraction may be incomplete.

Unknown skill candidates must remain pending suggestions and must not be converted into verified skills automatically.

## 9. Matching and Scoring Plan

For the selected job:

- call `match_skills(profile["skills"], job)` for required/preferred evidence;
- call `match_education(profile["education"], job)`;
- call `match_experience(profile, job)` with a fixed test date in unit tests;
- call `match_candidate_projects(profile, job)`;
- call `evaluate_candidate_job(profile, job, project_result, quality_result)`.

Display:

- matched skills and missing required/preferred skills;
- education matched, missing, and manual-review entries;
- parsed experience entries, total/relevant months, status, and review reasons;
- grouped project titles, project evidence, and grouping caution;
- quality issues/warnings;
- overall score only if available;
- score coverage and component coverage;
- manual-review reasons.

Do not interpret the score as a hiring recommendation or automatic rejection. A low score must be described as a missing-evidence indicator.

## 10. CSV and JSON Downloads

The download payload is session-only and will contain no original upload bytes or raw resume content.

### Privacy defaults for CSV and JSON

By default, neither download format may include:

- `full_text` or extracted paragraph/text blocks;
- the original uploaded filename;
- raw evidence lines or raw resume snippets;
- personal names, email addresses, phone numbers, addresses, or other personal information identified in the text.

Downloads must use only a generic processing ID such as `UPL-AB12CD34` and a generic source label such as `Uploaded resume`. Matched skill names, high-level education/experience status, quality messages, project titles, and manual-review reasons may be included only when they do not embed raw personal text.

The original resume text can be retained temporarily in Streamlit session state solely for current in-memory processing and display control. It must not be logged and must not be added to downloadable JSON/CSV. Streamlit session state is temporary application state, not a guaranteed secure private vault. The UI must say that users should not upload sensitive or confidential information and must use synthetic documents for this portfolio demo.

### CSV

Generate in memory with Python `csv` or Pandas:

- generic candidate processing ID;
- generic source label;
- selected job ID/title;
- overall score and coverage;
- evaluation status;
- component points/coverage;
- matched/missing skill names;
- education/experience/project status;
- quality status/issues/warnings;
- manual-review reasons;
- no original filename and no raw text/evidence.

The CSV filename uses the processing ID and contains no candidate name or original filename.

### JSON

Generate in memory with a top-level structure such as:

```json
{
  "processing_id": "UPL-...",
  "mode": "resume_analysis",
  "human_review_required": true,
  "job": {"job_id": "...", "job_title": "..."},
  "profile": {
    "candidate_id": "UPL-...",
    "source_label": "Uploaded resume",
    "skills": [],
    "education_status": {},
    "experience_status": {},
    "project_status": {},
    "verification_required": true
  },
  "quality": {},
  "skill_match": {},
  "education_match": {},
  "experience_match": {},
  "project_match": {},
  "scoring": {}
}
```

Do not include `full_text`, `skill_evidence`, `potential_skill_candidates` raw evidence, `source_file`, or raw project/experience evidence in this payload. The JSON/CSV export should include generic summary fields and sanitized match statuses only. Raw text export must not be offered as an implicit or default option.

## 14. Privacy and Deployment Risks

1. Streamlit session state may survive reruns, so clear/reset uploaded text and profiles on a new upload or session control.
2. Do not log original filenames, extracted text, email addresses, phone numbers, or parser exceptions containing file content.
3. Generic source labels and ephemeral IDs reduce accidental personal-data exposure in downloads.
4. The app must not write uploaded documents to the repository or batch folders.
5. Demo fixtures must be independently reviewable and free of real personal data.
6. Existing private folders must remain local and ignored; synthetic Demo Mode must not fall through to them.
7. Existing report loaders can reveal filenames or absolute paths in warnings. UI-facing errors should prefer filenames or generic messages, not absolute host paths.
8. `python-docx` parsing untrusted ZIP/XML content is not an authorization boundary; file size and extension checks must remain coupled with parser exception handling.
9. Streamlit Community Cloud deployment cannot assume a persistent disk or private batch data.
10. Candidate scores are decision-support only and should display the human-review disclaimer on every relevant view.
11. Backups and alternate implementations must not be referenced in cloud imports.
